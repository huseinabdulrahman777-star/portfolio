SAÉ 11 - Sécurisation d’un accès distant SSH

Description / Objectif

Dans le cadre de la SAE11, j’ai mis en place un accès distant sécurisé avec le protocole SSH sur une machine Debian. L’objectif était de comprendre le fonctionnement d’un serveur SSH ainsi que les différentes méthodes permettant de renforcer la sécurité d’une connexion distante.

Afin d’améliorer la sécurité du serveur, j’ai modifié le port SSH par défaut utilisé par le service OpenSSH.

Apprentissages Critiques (AC)

  • AC11.03 — Configurer les fonctions de base du réseau local
  • AC11.04 — Maîtriser les rôles et les principes fondamentaux des systèmes d’exploitation
  • AC11.05 — Identifier les dysfonctionnements du réseau local et savoir les signaler

Problème rencontré

Après avoir modifié la configuration du serveur SSH et redémarré le service, les connexions distantes ne fonctionnaient plus correctement.

Lors d’une tentative de connexion avec la commande : ssh utilisateur@adresse_ip, le terminal affichait une erreur de connexion.

Figure 1 — Échec de connexion SSH après modification du port.

Analyse du problème

Après plusieurs vérifications, j’ai constaté que le serveur SSH n’utilisait plus le port 22 par défaut.

Le service SSH avait été configuré pour écouter sur le port 3333 afin de limiter les tentatives d’attaques automatiques ciblant le port standard SSH.

Le problème ne provenait donc pas du service SSH lui-même, mais du port utilisé lors de la connexion distante.

Résolution du problème

Pour corriger cette erreur, j’ai indiqué manuellement le nouveau port SSH dans la commande de connexion grâce à l’option : -p

Commande utilisée :

ssh -p 3333 utilisateur@adresse_ip

Après cette correction, la connexion SSH au serveur Debian a fonctionné correctement.

Figure 2 — Connexion SSH réussie après utilisation du bon port.

Il restait simplement à entrer le mot de passe afin de terminer l’authentification.

Compétences développées

  • Compréhension du fonctionnement du protocole SSH
  • Utilisation des ports réseau
  • Configuration d’un serveur OpenSSH
  • Sécurisation d’un accès distant
  • Diagnostic et résolution d’un problème réseau

Autoévaluation

Cette situation m’a permis de développer mes compétences en administration système et en sécurisation des accès distants. J’ai appris à identifier rapidement l’origine d’un problème de connexion SSH et à vérifier les paramètres réseau utilisés.

Cette expérience m’a également montré l’importance de tester une configuration après modification et de bien vérifier les ports utilisés par les services réseau.

SAÉ 12 — Administration de services réseau sous Debian

Description / Objectif

Dans le cadre de la SAE12, j’ai installé et configuré plusieurs services réseau sur une machine Debian afin de comprendre le fonctionnement des services Linux en environnement réseau.

Cette SAE m’a permis de travailler sur un serveur web Apache ainsi que sur un serveur DHCP afin de mettre en place des services accessibles depuis un réseau local.

Apprentissages Critiques (AC)

  • AC11.03 — Configurer les fonctions de base du réseau local
  • AC11.04 — Maîtriser les systèmes d’exploitation
  • AC11.05 — Identifier les dysfonctionnements réseau
  • AC11.06 — Installer et configurer un poste client

Problème 1 — Serveur Apache inaccessible depuis le réseau

Après l’installation du serveur Apache, le site web fonctionnait correctement sur la machine Debian elle-même, mais les autres machines du réseau ne pouvaient pas accéder au serveur web.

Lors d’un test avec la commande : curl 192.168.10.62, une erreur de connexion apparaissait.

Figure 1 — Échec de connexion HTTP depuis le poste client.

Analyse du problème

Après plusieurs vérifications, j’ai constaté que le serveur Apache écoutait uniquement sur l’interface locale : 127.0.0.1.

Cette configuration empêchait les connexions provenant des autres machines du réseau local.

Résolution du problème

Pour corriger cette erreur, j’ai modifié le fichier :

/etc/apache2/ports.conf

La configuration : Listen 127.0.0.1:80 a été remplacée par : Listen 80

Après redémarrage du service Apache :

sudo systemctl restart apache2

le site web est devenu accessible depuis les autres machines du réseau.

Figure 2 — Accès réussi au serveur Apache après correction.

Problème 2 — Le serveur DHCP ne distribuait plus d’adresse IP

Dans cette seconde partie de la SAE, j’ai configuré un serveur DHCP afin d’automatiser l’attribution des adresses IP aux postes du réseau local.

Lors des tests, le poste client ne recevait plus d’adresse IPv4 automatiquement.

Figure 3 — Absence d’adresse IP sur le poste client.

Analyse du problème

Après plusieurs vérifications, j’ai constaté que l’interface réseau utilisée par le serveur DHCP n’était pas correctement configurée.

Le message suivant apparaissait :

No subnet declaration for eth0

Le problème provenait donc de la configuration réseau du serveur DHCP.

Résolution du problème

Pour corriger cette erreur, j’ai configuré une adresse IP statique sur l’interface réseau du serveur Debian.

auto eth0
iface eth0 inet static
address 192.168.1.65
netmask 255.255.255.0

Figure 4 — Configuration de l’adresse IP statique du serveur.

Après redémarrage du réseau et du service DHCP :

sudo systemctl restart networking

sudo systemctl restart isc-dhcp-server

les postes clients ont reçu automatiquement une adresse IP valide.

Figure 5 — Attribution correcte d’une adresse IP au poste client.

Compétences développées

  • Configuration d’un serveur Apache sous Debian
  • Configuration d’un serveur DHCP
  • Diagnostic de problèmes réseau
  • Gestion des services Linux avec systemctl
  • Compréhension des échanges client/serveur

Autoévaluation

Cette SAE m’a permis de renforcer mes compétences en administration système et réseau sous Linux.

J’ai appris à diagnostiquer des problèmes d’accessibilité réseau et à analyser les configurations des services Linux.

Cette expérience m’a également montré l’importance des interfaces réseau et de la configuration correcte des services dans un environnement client/serveur.
